# EIM-MVP-006 — الحزمة الخامسة: المقترحات والعقود والمشاريع والمال

**الإصدار:** V113  
**المتطلبات المالكة:** MVP-SVC-001..003 وMVP-PRJ-001..004 وMVP-FIN-001..004  
**المسارات:** J09 وJ10 وJ12  
**الحالة:** تصميم تفصيلي مكتمل؛ التوقيع والدفع والتخزين والتوطين القانوني الحي لاحق.

## 1. الهدف

تحدد الحزمة دورة القيمة الملزمة من طلب الخدمة المنشور إلى الإغلاق المالي والتنفيذي، وتمنع الخلط بين الاستجابة والمقترح والعقد والمشروع، وبين التسليم والاستلام والقبول، وبين الفاتورة ومحاولة الدفع والدفعة والتسوية والاسترداد.

## 2. سلسلة الكيانات المرجعية

```text
ServiceRequest
  → ProviderResponse
  → Proposal → ProposalVersion[*]
  → Contract → Signature[*]
  → Project → Baseline → Milestone[*] → Deliverable[*] → AcceptanceDecision[*]
  → InvoiceEligibility → Invoice → PaymentAttempt[*] → Payment → Settlement[*]
  → Refund[*] / CreditNote[*]
```

ويعمل مسار الاشتراك بالتوازي:

```text
SubscriptionPlan → PriceVersion → Subscription → SeatAllocation[*]
                 → Invoice → Payment → Activation/Renewal
```

## 3. الحدود غير القابلة للدمج

| الكيان | الحقيقة التي يملكها | لا يساوي |
|---|---|---|
| ProviderResponse | جواب مقدم بعينه على طلب بعينه | عرضًا عامًا أو عقدًا |
| ProposalVersion | شروط فنية وتجارية مقترحة بإصدار | العقد النافذ |
| Contract | الالتزام القانوني الموقع | المشروع أو الفاتورة |
| Project | إطار التنفيذ والحوكمة | العقد نفسه |
| Baseline | نطاق وزمن وتكلفة معتمدة | آخر خطة عمل غير معتمدة |
| Deliverable | الشيء المسلم وإصداراته | الاستلام أو القبول |
| AcceptanceDecision | قرار مقابل معيار قبول | رفع الملف أو تأكيد الاستلام |
| InvoiceEligibility | تحقق استحقاق الفوترة | فاتورة أو دفعًا |
| Invoice | مطالبة مالية مرقمة | محاولة دفع أو دفعة |
| PaymentAttempt | تفاعل مع وسيلة/بوابة دفع | حركة مالية مستقرة |
| Payment | قيمة مستلمة ومؤكدة | تسوية المزود أو الاسترداد |
| Settlement | توزيع/إقفال مالي بين الأطراف | دفع العميل |
| Refund | عكس كلي/جزئي موثق | حذف الدفع الأصلي |
| Subscription | حق استخدام زمني لخطة | عضوية مهنية أو حساب |

## 4. استجابة مقدم الخدمة

### دورة الحياة

`Draft → Interested | Declined → Submitted → ClarificationRequested → Revised → AcceptedForProposal | NotSelected | Withdrawn | Expired`

### المحتوى الإلزامي

- مرجع طلب الخدمة وإصداره.
- الطرف/العضوية المقدمة للاستجابة.
- فهم مختصر للاحتياج.
- نطاق الاستجابة والمخرجات التي يستطيع تقديمها.
- الدور والمساهمة والفريق المقترح إن وجد.
- التوفر ونمط التنفيذ والموقع واللغة.
- تقدير مدة بالأيام عندما يطلب الحقل مدة.
- تقدير مالي أولي أو «يتطلب استيضاحًا».
- الافتراضات والاستثناءات والمخاطر.
- صلاحية الاستجابة ومستوى السرية.

### قواعد

1. لا يطلع مقدم الخدمة إلا على الحقول المصرح بها.
2. إعادة إرسال الطلب نفسه بمفتاح واحد لا تنشئ استجابتين.
3. `Declined` يحفظ سببًا داخليًا وتصنيفًا قابلًا للتحليل، دون إلزام بالإفصاح للعميل.
4. الاستجابة المقبولة تفتح إنشاء مقترح؛ لا تنشئ عقدًا.
5. كل تعديل بعد الإرسال ينشئ Revision.

## 5. المقترح والتفاوض

### محتوى ProposalVersion

- نسخة الاحتياج والطلب والاستجابة المرجعية.
- النطاق والمستثنيات والمنهجية.
- التسليمات ومعايير القبول.
- الفريق والأدوار والمساهمة والتوفر.
- الخطة والمعالم والمدة.
- السعر والعملة والضرائب وشروط الدفع.
- الافتراضات والاعتماديات والمخاطر.
- الملكية الفكرية والترخيص والسرية.
- مدة الصلاحية وشروط الانسحاب والتغيير.

### دورة الحياة

`Draft → Submitted → UnderClientReview → Clarification → Countered → Revised → Accepted | Rejected | Withdrawn | Expired`

### قواعد التفاوض

1. المقترح المقبول immutable؛ وأي تعديل لاحق ينشئ نسخة واتفاقًا جديدًا.
2. قرار `Countered` يحدد البنود المتغيرة ولا يكتب فوق نسخة الطرف الآخر.
3. يقارن النظام الإصدارات بندًا ببند: نطاق، وقت، سعر، حقوق، مخاطر.
4. لا يملك المستخدم قبول المقترح إلا ضمن تفويض فني ومالي مناسب.
5. انتهاء الصلاحية يمنع القبول دون إعادة تأكيد المزود.

## 6. العقد والتوقيع

### إنشاء العقد

ينشأ عقد واحد من ProposalVersion مقبولة، ويحتفظ بالمراجع والنسخة والتجزئة. لا تنسخ المالية عقدًا ثانيًا.

### دورة الحياة

`Draft → InternalReview → ReadyForSignature → PartiallySigned → FullySigned → Active → Suspended → Completed | Terminated | Expired`

### شروط النفاذ

- هوية قانونية صحيحة لكل طرف.
- ممثل مخول وفترة/حدود سلطة سارية.
- نسخة شروط نهائية واحدة وتجزئة ثابتة.
- توقيعات جميع الأطراف المطلوبة.
- تحقق شروط سابقة إن وجدت: دفعة مقدمة، NDA، ضمان، وثيقة.
- وقت نفاذ وقانون حاكم واختصاص قضائي وفق التوطين.

### قواعد

1. التوقيع مرتبط بالموقع والصفة والوقت والنسخة.
2. تغيير أي بند بعد توقيع طرف يبطل دورة التوقيع السابقة ويطلب نسخة جديدة.
3. `FullySigned` لا يعني `Active` إذا بقي شرط سابق.
4. إنهاء العقد حدث له سبب وأثر مالي وحقوقي؛ لا يحذف المشروع.
5. المستند الموقع والأدلة تحفظ في تخزين آمن وروابط موقعة.

## 7. إنشاء المشروع وخط الأساس

لا ينشأ المشروع التنفيذي إلا من عقد Active أو تفويض داخلي خاص معتمد.

### دورة حياة المشروع

`Initiating → Planning → BaselinePending → Active → OnHold → Closing → Closed | Cancelled | Terminated`

### مكونات خط الأساس

- النطاق والتسليمات والاستثناءات.
- هيكل العمل والمسؤوليات.
- المعالم والتواريخ والاعتماديات.
- الميزانية وخطة الفوترة.
- معايير القبول والمراجعين والموافقين.
- خطة التواصل والتقارير.
- المخاطر والقضايا والافتراضات.
- السرية والحقوق وإدارة الملفات.

### قواعد

1. العقد يحدد الالتزام؛ والخط الأساسي ينظمه للتنفيذ دون تجاوزه.
2. بدء العمل قبل اعتماد Baseline يحتاج استثناءً مؤقتًا مخولًا ومسببًا.
3. لا يعدل Baseline المعتمد مباشرة؛ يستخدم ChangeOrder.
4. العضو في فريق مقترح لا يصبح عضو مشروع قبل التكليف وقبول الشروط.

## 8. المعالم والتسليمات والقبول

### التسليم

`Draft → Submitted → Received → UnderReview → Accepted | Rejected | ChangesRequested → Resubmitted → Superseded`

### الفصل بين الأحداث

| الحدث | المعنى | الأثر المالي |
|---|---|---|
| Submitted | المزود رفع إصدارًا | لا أثر تلقائي |
| Received | المنصة/العميل أكد وصوله | لا يعني قبولًا |
| UnderReview | بدأت المراجعة | لا أثر تلقائي |
| Accepted | استوفى معايير محددة بقرار مخول | قد يولد InvoiceEligibility |
| Rejected | لم يستوفِ مع سبب وأدلة | لا يمحو التسليم |
| ChangesRequested | مطلوب تعديل محدود | ينشئ إعادة تقديم |

### قرار القبول

- يحدد معيار القبول والنتيجة والدليل والمراجع والوقت.
- يسمح بقبول كامل أو جزئي فقط إذا سمح العقد وحدد أثره المالي.
- الصمت لا يعد قبولًا إلا إذا نص عقد معتمد بوضوح، مع إشعارات ومهلة.
- رفض التسليم مسبب وقابل للمعالجة/التصعيد وفق العقد.

## 9. إدارة التغيير

### دورة ChangeOrder

`Draft → ImpactAnalysis → Submitted → CounterpartyReview → Approved | Rejected | Withdrawn | Expired → Applied → Verified → Closed`

### تحليل الأثر

- السبب والمصدر.
- النطاق والتسليمات المتأثرة.
- الوقت والتكلفة والموارد.
- الجودة والمخاطر والحقوق والسرية.
- أثر العقود والفواتير والاشتراكات والتكاملات.

### قواعد

1. لا يطبق التغيير قبل موافقة الأطراف المخولة.
2. الموافقة تنشئ BaselineRevision وعقدًا ملحقًا عند اللزوم.
3. الرفض والسحب يبقيان السجل ولا يعدلان الأساس.
4. التغيير الطارئ له مسار استثناء محدود ومراجعة لاحقة.

## 10. المخاطر والقضايا والقرارات والتقدم

| السجل | الغرض | حالات نموذجية |
|---|---|---|
| ProjectRisk | حدث محتمل وتأثير واستجابة | Open, Treating, Accepted, Closed |
| ProjectIssue | مشكلة واقعة تحتاج حلًا | Open, Assigned, Resolving, Resolved, Closed |
| ProjectDecision | قرار وسياق وبدائل ومخول | Proposed, Approved, Rejected, Superseded |
| ProgressReport | تقدم فترة وخطة وانحراف | Draft, Submitted, Reviewed, Accepted |

لا يغلق المشروع إذا بقيت تسليمات أو فواتير أو قضايا أو حقوق أو ملفات أو شكاوى مانعة وفق السياسة.

## 11. أهلية الفوترة والفاتورة

### مصادر الأهلية

- قبول تسليم/معلم.
- دفعة مقدمة عند نفاذ العقد.
- قسط زمني وفق عقد.
- اشتراك أو تجديد.
- تسجيل في طرح تدريبي.
- رسم خدمة منصوص عليه.

### دورة InvoiceEligibility

`Detected → Validating → Eligible | Blocked | Waived → Invoiced`

### دورة الفاتورة

`Draft → Issued → Delivered → PartiallyPaid → Paid | Overdue | Disputed | Voided | WrittenOff`

### قواعد

1. رقم الفاتورة فريد ومتسلسل وفق الكيان/الدولة والسياسة.
2. الفاتورة المصدرة لا تعدل؛ يصحح الخطأ بإلغاء/إشعار دائن وفاتورة بديلة.
3. العملة في الفوترة من القائمة المعتمدة للـMVP: دولار أو يورو، مع قابلية توطين لاحقة.
4. مبلغ كل بند والضريبة والإجمالي والتقريب قابلة لإعادة الحساب.
5. الفاتورة المتنازع عليها لا تحذف ولا تعد مدفوعة.

## 12. محاولات الدفع والدفعات والتسوية

### محاولة الدفع

`Created → Redirected/Authorized → Processing → Succeeded | Failed | Cancelled | Expired`

### الدفعة

`PendingConfirmation → Confirmed → Allocated → Settled | PartiallyRefunded | Refunded | Reversed`

### قواعد

1. لا تخزن المنصة بيانات بطاقة حساسة؛ تستخدم Token/مرجع مزود.
2. نتيجة واجهة العميل لا تكفي؛ التأكيد من Webhook موقع أو تسوية موثوقة.
3. Webhook يستخدم idempotency key وتحقق توقيع ووقت ومنع replay.
4. دفعة واحدة يمكن تخصيصها لعدة بنود وفق سياسة؛ ويحفظ التخصيص.
5. اختلاف حالة المزود والمنصة يفتح ReconciliationCase.

## 13. الاسترداد والإشعار الدائن

### الاسترداد

`Requested → EligibilityReview → Approved | Rejected → SubmittedToProvider → Processing → Completed | Failed`

### قواعد

- كلي أو جزئي ضمن الرصيد القابل للاسترداد.
- سبب ومرجع سياسة وموافق وحد مالي.
- لا يغير مبلغ Payment الأصلي؛ ينشئ Refund وحركات دفترية عكسية.
- عند فشل المزود يبقى الطلب قابلًا لإعادة المحاولة دون تكرار.
- الإلغاء أو النزاع أو الاسترداد يحدث الاشتراك/التسجيل/المشروع وفق السياسة لا تلقائيًا بلا قاعدة.

## 14. الاشتراكات والباقات والتجديد

### متغيرات التسعير

- فرد أو مؤسسة.
- شهر أو سنة.
- الخطة: مجانية/فضية/ذهبية أو الأسماء التجارية المعتمدة.
- عدد العضويات للفرد أو المقاعد/المستخدمين للمؤسسة.
- إصدار السعر والعروض والضرائب.

### دورة الاشتراك

`Draft → PendingPayment → Active → GracePeriod → PastDue → Suspended → Cancelled | Expired → Renewed`

### قواعد

1. العضوية المهنية لا تساوي الاشتراك؛ انتهاء الاشتراك يحد مزايا الخطة وفق السياسة ولا يمحو الملف.
2. التجديد اليدوي أو التلقائي ينشئ فاتورة ودورة دفع جديدة.
3. تغيير الخطة يحسب الأثر وفق سياسة prorating معتمدة ومفسرة.
4. إلغاء التجديد التلقائي لا يلغي الفترة المدفوعة الحالية إلا إذا اختار المستخدم خلاف ذلك وفق السياسة.
5. تنبه المنصة قبل التجديد والخصم وانتهاء المهلة.

## 15. الإغلاق التنفيذي والمالي

### بوابة إغلاق المشروع

- كل التسليمات النهائية Accepted أو معالجة بقرار.
- جميع ChangeOrders مغلقة أو مؤرشفة بقرار.
- المخاطر والقضايا المانعة مغلقة/مقبولة رسميًا.
- الفواتير والمدفوعات والتسويات بحالة تسمح بالإغلاق.
- تسليم الحقوق والملفات والمعرفة وفق العقد.
- شهادة إغلاق وتقييم الأطراف متاحان.

الإغلاق المالي لا يعني حذف صلاحية الوصول فورًا؛ تطبق مدة حفظ ووصول ما بعد المشروع.

## 16. الصلاحيات وفصل المهام

| الإجراء | المنشئ | المراجع/الموافق | منع الجمع الافتراضي |
|---|---|---|---|
| استجابة | مقدم الخدمة | العميل | مقدم الخدمة لا يختار نفسه |
| قبول مقترح | صاحب الطلب | مالي/فني حسب الحد | لا قبول خارج التفويض |
| توقيع عقد | ممثل مخول | تحقق قانوني/داخلي | منشئ المسودة ليس بالضرورة الموقع |
| قبول تسليم | مراجع فني | صاحب قبول مخول | منفذ التسليم لا يقبله |
| إصدار فاتورة | مالية | اعتماد وفق الحد | لا اعتماد ذاتي عند الحدود الحساسة |
| استرداد | دعم/مالية | موافق مستقل | طالب الاسترداد لا يعتمده |
| تسوية | نظام/مالية | مراجعة مصالحة | لا تعديل يدوي بلا أثر |

## 24. معايير إغلاق الحزمة

1. الاستجابة والمقترح والعقد والمشروع مستقلة ومترابطة.
2. التفاوض يحفظ كل إصدار والفرق والقرار.
3. العقد لا ينفذ دون هوية وصلاحية وتوقيعات وشروط.
4. المشروع لا ينشأ إلا من مرجع مخول.
5. التسليم والاستلام والقبول منفصلة.
6. التغيير لا يكتب فوق Baseline.
7. القبول يولد أهلية فوترة فقط.
8. الفاتورة والمحاولة والدفعة والتسوية والاسترداد منفصلة.
9. الاشتراك مستقل عن العضوية ويحفظ إصدارات السعر والفترات.
10. كل حركة قانونية ومالية قابلة للتدقيق وغير قابلة للحذف الصامت.

**القرار:** الحزمة الخامسة مكتملة تصميميًا لمتطلبات SVC وPRJ وFIN. تبقى L وA معلقتين على مزودي التوقيع والدفع والتخزين، التوطين القانوني والضريبي، المصالحة، واختبارات E2E والأمن وUAT الحية.
