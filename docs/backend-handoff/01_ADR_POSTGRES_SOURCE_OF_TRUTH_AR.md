# ADR-001 — PostgreSQL مصدر الحقيقة الإنتاجي

**الحالة:** مقترح ملزم للتنفيذ بعد توقيع أصحاب القرار  
**الإصدار:** V113 R5  
**التاريخ:** 1 أغسطس 2026

## السياق

يعمل العرض الحالي على Cloudflare D1، بينما يضم PostgreSQL النموذج المؤسسي
الكامل للهوية والعضويات والتصنيف والمطابقة والعقود والمشاريع والمال والحوكمة.
استمرار الكتابة المستقلة في القاعدتين يخلق تعارضاً وفقداً للتتبع.

## القرار

1. PostgreSQL 16 هو النظام القياسي المسجل System of Record.
2. D1 طبقة مؤقتة للعرض والتوافق، وتقرأ من خدمات Backend أو نسخ إسقاطية فقط.
3. يمنع إنشاء وظيفة أعمال جديدة تعتمد D1 بوصفه المصدر النهائي.
4. كل أمر كتابة جديد يمر بخدمة Backend واحدة ومعاملة PostgreSQL واحدة.
5. تستخدم الأحداث وOutbox لبناء الإسقاطات والتكاملات؛ لا تستخدم الكتابة المزدوجة المباشرة.
6. الملفات الثنائية تبقى في Object Storage خاص؛ PostgreSQL يحفظ metadata والسياسات والسجل.

## ملكية المجالات

| المجال | المصدر النهائي | ملاحظات |
|---|---|---|
| الهوية والحسابات | PostgreSQL/IAM provider | لا تحفظ كلمات مرور خام |
| الأطراف والمنظمات | PostgreSQL `core` | `core.parties` السجل الموحد |
| العضويات | PostgreSQL `membership` | انتقالات محكومة ومؤرخة |
| التصنيف والأنطولوجيا | PostgreSQL `taxonomy` | بإصدارات منشورة |
| الأدلة والملفات | PostgreSQL + Object Storage | الروابط موقعة ومحدودة |
| العميل والاحتياج | PostgreSQL `crm/needs` | الإصدار المجمد أساس المطابقة |
| المطابقة والفرق | PostgreSQL `matching/delivery` | نتائج قابلة للتفسير |
| العقود والمشاريع | PostgreSQL `contract/delivery` | أوامر idempotent |
| الفواتير والمدفوعات | PostgreSQL `finance` + PSP | التسوية من webhook موثق |
| الحوكمة والتدقيق | PostgreSQL `governance/audit` | سجلات append-only |

## مراحل الانتقال

1. **Inventory:** مطابقة كل جدول وEndpoint في D1 مع مالكه في PostgreSQL.
2. **Read shadow:** قراءة PostgreSQL ومقارنة النتيجة مع D1 دون تغيير المستخدم.
3. **Domain cutover:** تحويل الكتابة مجالاً بعد مجال إلى PostgreSQL.
4. **Projection:** تحديث D1، إن بقي مطلوباً، من Outbox فقط.
5. **Retirement:** إيقاف جداول D1 المنقولة بعد فترة تحقق ومصالحة.

## ضوابط الانتقال

- correlation ID وidempotency key لكل أمر حساس.
- مقارنة counts وchecksums وسجلات رفض عند كل cutover.
- لا حذف قبل نسخة احتياطية واختبار استعادة واعتماد مالك البيانات.
- rollback في cutover يعني إعادة توجيه الحركة، لا حذف سجلات PostgreSQL المنشأة.

## النتائج المترتبة

- يحتاج التطبيق إلى Backend adapter دائم بدلاً من SQL موزع داخل Routes.
- يجب تحويل API الحالية تدريجياً مع الحفاظ على OpenAPI.
- تتراجع بساطة D1 مقابل اتساق أقوى وعزل مؤسسي ومعاملات وRLS ممكنة.
