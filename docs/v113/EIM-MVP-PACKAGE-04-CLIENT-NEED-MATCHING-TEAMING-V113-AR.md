# EIM-MVP-005 — الحزمة الرابعة: إدارة العميل والاحتياج والمطابقة وتكوين الفرق

**الإصدار:** V113  
**المتطلبات المالكة:** MVP-CLI-001..004 وMVP-NEED-001..005 وMVP-MAT-001..007  
**المسارات:** J06 وJ07 وJ08  
**الحالة:** تصميم تفصيلي مكتمل؛ المعايرة والبيانات والخدمات الحية وUAT لاحقة.

## 1. هدف الحزمة

تحول هذه الحزمة العميل من سجل اتصال بسيط إلى طرف فردي أو مؤسسي محكوم، وتحول طلبه من نص عام إلى بصمة احتياج قابلة للمقارنة، ثم تدير مطابقة مفسرة تحترم الأهلية والأوزان ودرجة اليقين وتنتهي بخيارات وقرار بشري وتكوين فريق، لا بقرار آلي ملزم.

## 2. النموذج المفاهيمي

```text
ClientParty(Person|Organization)
  ├─ ClientProfile
  ├─ OrganizationUnit[0..n]
  ├─ AuthorizedRepresentative[1..n]
  ├─ ClientOpportunity[0..n]
  └─ ClientNeed[0..n]
       └─ NeedVersion[1..n]
            ├─ TaskFingerprint[1]
            ├─ ServiceRequest[0..1]
            └─ MatchingRun[0..n]
                 ├─ EligibilityDecision[*]
                 ├─ CandidateScore[*]
                 ├─ MatchExplanation[*]
                 ├─ Shortlist[0..1]
                 └─ ClientDecision[0..n]
                      └─ ExpertTeam[0..1]
                           └─ TeamMemberAssignment[1..n]
```

### حدود أساسية

- `ClientProfile` يصف العميل؛ لا يساوي حساب المستخدم الممثل له.
- `ClientOpportunity` فرصة علاقة/بيع؛ لا تساوي احتياجًا أو التزامًا تعاقديًا.
- `ClientNeed` الغرض والمشكلة؛ لا يساوي `ServiceRequest` المنشور.
- `NeedVersion` سجل تطور الاحتياج؛ و`TaskFingerprint` تمثيل منظم للنسخة.
- `MatchingRun` تشغيل تحليلي؛ لا يساوي قرار العميل.
- `CandidateScore` نتيجة مرشح داخل تشغيل؛ لا تصبح سمعة عامة.
- `Shortlist` أداة قرار؛ لا تعد عرضًا أو عقدًا.
- `ExpertTeam` فريق مقترح/مقبول؛ لا يصبح فريق مشروع قبل العقد والتكليف.

## 3. أنواع العملاء السبعة

| النوع | طبيعة الطرف | متطلبات إضافية | سلطة القرار |
|---|---|---|---|
| فردي مستقل | Person | هوية وتواصل وفوترة عند الحاجة | صاحب الحساب |
| مؤسسة أو شركة خاصة | Organization | سجل قانوني وممثلون وفروع وفوترة | مفوض حسب حدود السلطة |
| قطاع أكاديمي | Organization | جهة/كلية/قسم، غرض علمي أو تدريبي | مفوض أكاديمي/إداري |
| قطاع مشترك | Organization | أطراف الملكية وطبيعة التفويض | مفوض وفق النظام |
| منظمة حكومية | Organization | مرجع رسمي وقيود شراء واعتماد | صاحب صلاحية مالية/فنية |
| منظمة إقليمية | Organization | دولة المقر والولاية والنطاق | مفوض إقليمي |
| منظمة دولية | Organization | المقر والبرنامج والجهات المستفيدة | مفوض البرنامج/المشتريات |

نوع العميل يحدد حقول الهوية والوثائق وسلسلة الاعتماد، لكنه لا يحدد الخدمة المطلوبة.

## 4. صفة التسجيل/الغرض الأولي

القائمة المعتمدة:

1. طلب استشارة متخصصة.
2. طلب تدريب أو ورش عمل.
3. طلب إدارة أو دعم مشروع.
4. طلب تقييم أو مراجعة (Audit / Review).
5. طلب خبير للانضمام إلى فريق عمل مؤقت.
6. طلب دراسات أو أبحاث تطبيقية.

هذه الصفة توجه البداية فقط، ويمكن للعميل لاحقًا إنشاء احتياجات متعددة من أنواع مختلفة.

## 6. دورة حياة العميل والفرصة

### ملف العميل

`Draft → Verified → Active → Restricted | Suspended → Closed`

### الفرصة

`Identified → Qualified → Discovery → NeedDrafted → RequestIssued → ProposalStage → Won | Lost | OnHold → Closed`

قواعد:

1. تحول الفرصة إلى احتياج ينشئ رابطًا، ولا يحول السجل نفسه إلى احتياج.
2. `Won` لا تعني دفعًا أو عقدًا نافذًا؛ يلزم العقد ودورة المال.
3. تحفظ أسباب `Lost` و`OnHold` كبيانات تعلم، مع وصول مقيد.

3. كل قيمة حساسة تحمل قرار إفصاح عند النشر أو الدعوة.
4. التغيير الجوهري بعد التجميد ينشئ `NeedVersion` جديدة.
5. تحتفظ المطابقة بمرجع نسخة البصمة، فلا يعاد تفسير نتيجة قديمة ببيانات جديدة.

## 9. بوابة اكتمال الاحتياج

### مشترك P0

- العنوان والغرض والنوع القائد.
- مالك الاحتياج وصاحب قرار القبول.
- مسار تصنيف أساسي واحد على الأقل.
- مخرج واحد على الأقل ومعيار قبول مقابل له.
- موعد أو مدى زمني.
- ميزانية رقمية بالدولار أو اليورو، أو «غير معلنة/تطلب عرضًا» كحالة صريحة.
- نمط التنفيذ والدول/الموقع عند الحاجة.
- مستوى السرية وسياسة الإفصاح.
- أنواع الخدمات المطلوبة من القائمة المعتمدة.

### قائمة أنواع الخدمات المطلوبة

`بحث جديد، تطوير منتج، استشارات، دراسات موضوعية، إعداد دراسات جدوى فنية واقتصادية، تصميم أو إيجاد نماذج، إدارة مشاريع، تنفيذ مشاريع تطبيقية، إشراف، تدقيق، تقييم، تحكيم، تدريب`

## 10. دورة حياة الاحتياج والطلب

### الاحتياج

`Draft → Clarifying → Complete → Frozen → Superseded | Cancelled → Archived`

### طلب الخدمة

`Draft → InternalReview → Approved → Published/Invited → Open → Paused → Closed → Awarded | Cancelled`

قواعد:

1. لا ينشر طلب من نسخة احتياج غير `Frozen`.
2. لا يعدل الطلب المنشور بصمت؛ التغيير الجوهري ينشئ إصدارًا وإشعارًا.
3. `Awarded` يحدد المرشح المختار ولا ينشئ عقدًا نافذًا تلقائيًا.
4. الإلغاء يحفظ الدعوات والاستجابات والقرارات السابقة.
5. تمنع إعادة المحاولة من تكرار الطلب أو الدعوات.

## 12. الأهلية قبل المطابقة

الأهلية قرار منفصل لا يحمل نقاط ترتيب.

### أمثلة شروط الأهلية

- عضوية Approved وفعالة.
- نوع مهني/مؤسسي مناسب.
- تخصص أو ترخيص إلزامي.
- دولة أو حق عمل/تقديم عند اللزوم.
- لغة إلزامية.
- توفر خلال نافذة زمنية.
- عدم تعارض مصالح أو عقوبة أو تعليق.
- قبول مستوى السرية وNDA عند الحاجة.
- حقوق صحيحة لاستخدام المحتوى أو المنهج.
- حد أدنى موثق من الأدلة عندما يكون إلزاميًا.

### مخرجات القرار

`Eligible | ConditionallyEligible | Ineligible | UnknownNeedsReview`

كل استبعاد يحمل سببًا وسياسة وإصدارًا، ويمكن مراجعته بشريًا إذا كان القرار مؤثرًا أو مبنيًا على معلومات ناقصة.

## 13. نموذج المطابقة الموزونة

### 13.1 فصل النتائج

تعرض المنصة ثلاث قيم منفصلة:

1. **درجة الملاءمة Fit:** مدى تطابق القيم المعروفة مع الاحتياج.
2. **تغطية المعلومات Coverage:** مقدار الأبعاد التي توفرت لها بيانات قابلة للتقييم.
3. **درجة اليقين Confidence:** قوة الأدلة وحداثتها والتحقق منها.

لا تعرض قيمة واحدة تخفي نقص المعلومات. ويمكن لسياسة ترتيب معتمدة احتساب «ترتيب معدل بالمخاطر»، بشرط إظهار مكوناته وعدم تغييرها دون إصدار.

### 13.2 أوزان العميل

- يحدد العميل وزن كل معيار ضمن الحدود التي تسمح بها السياسة.
- مجموع الأوزان الفعالة = 100%.
- المعايير الإلزامية لا تتحول إلى وزن؛ تبقى بوابة أهلية.
- يقدم النظام قالبًا مقترحًا قابلًا للتعديل، ولا يدعي أنه قرار العميل.
- تحفظ الأوزان مع إصدار ووقت ومستخدم وسبب عند التعديل الجوهري.

### 13.3 الحساب الأساسي

للمعايير المعروفة والقابلة للتقييم فقط:

```text
Fit = Σ(weight_i × normalized_match_i) / Σ(active_known_weights)
Coverage = Σ(active_known_weights) / Σ(all_active_weights)
Confidence = governed aggregation of evidence confidence by criterion
```

لا يساوي `Unknown` صفرًا؛ يخفض Coverage ويظهر كفجوة. لا تعتمد صيغة ترتيب معدل بالمخاطر قبل المعايرة على بيانات فعلية واعتماد السياسة.

### 13.4 تفسير النتيجة

لكل مرشح:

- الشروط التي اجتازها وفشل فيها أو تحتاج مراجعة.
- مساهمة كل معيار في Fit.
- الأدلة التي دعمت الدرجة ودرجة يقينها.
- المعلومات الناقصة.
- التعارضات أو القيود.
- أثر تعديل الوزن عند المحاكاة، دون تعديل التشغيل الأصلي.

## 14. تشغيل المطابقة

`Requested → Validating → EligiblePoolBuilt → Scoring → Completed | Failed | Cancelled → Superseded`

### اللقطة اللازمة لإعادة الإنتاج

- `need_version_id` و`task_fingerprint_version_id`.
- إصدار سياسة الأهلية.
- إصدار نموذج المعايير والأوزان.
- إصدار التصنيف والربط الدلالي.
- نسخ البصمات المهنية والأدلة المستخدمة.
- وقت قطع التوفر والأسعار والسمعة.
- إصدار الخوارزمية والإعدادات.
- جميع النتائج والتفسيرات وأسباب الاستبعاد.

|---|---|

### قرارات العميل

`Shortlisted | NotShortlisted | ClarificationRequested | Invited | Selected | NotSelected | Withdrawn`

العميل يكتب سببًا داخليًا اختياريًا أو إلزاميًا حسب السياسة، ويحدد ما يمكن مشاركته مع المرشح. لا يسمح بتعديل قرار نهائي بصمت؛ ينشأ حدث تصحيح أو قرار لاحق.

## 16. تكوين فريق الخبراء

### الهدف

اختيار مجموعة تكمل تغطية المهمة بدل جمع أعلى الدرجات الفردية فقط.

### القيود

- تغطية كل دور إلزامي.
- حد أدنى لليقين في الأدوار الحساسة.
- توفر متداخل كافٍ.
- عدم تعارض مصالح.
- قائد ومسؤوليات واضحة.
- ميزانية وعبء عمل ضمن الحدود.
- تنوع أو توزيع جغرافي عندما يكون متطلبًا مشروعًا، لا تمييزًا محظورًا.

### المخرجات

| الحقل | المعنى |
|---|---|
| TeamCoverage | تغطية المتطلبات والأدوار |
| MemberContribution | المساهمة الهامشية لكل عضو |
| Overlap | التكرار المفيد أو الزائد بين الأعضاء |
| Gaps | متطلبات غير مغطاة |
| Conflicts | توفر/مصلحة/حقوق/لغة/موقع |
| CostRange | تكلفة تقديرية لا عقدًا |
| Explanation | لماذا اقترح الفريق والبدائل |

### دورة حياة الفريق

`Draft → Proposed → MembersInvited → PartiallyAccepted → FullyAccepted → ClientApproved → Contracted → Active | Declined | Expired`

لا يصبح العضو جزءًا من الفريق قبل قبوله الدور والنطاق والوقت وشروط الإفصاح.

## 24. معايير إغلاق الحزمة

1. أنواع العملاء السبعة مرتبطة بحقوق وتمثيل مناسبين.
2. العميل المؤسسي يفصل المستخدم والممثل والوحدة والتفويض.
3. الاحتياج والطلب والفرصة كيانات مستقلة مترابطة.
4. كل نوع احتياج يملك بوابة اكتمال ومخرجات ومعايير قبول.
5. بصمة المهمة تحمل النسخة والسياق والقيود والإفصاح.
6. الأهلية تسبق الدرجات ولا تعوضها السمعة.
7. تظهر Fit وCoverage وConfidence منفصلة ومفسرة.
8. الأوزان نسخة يملك العميل قرارها ضمن السياسة.
9. القائمة المختصرة والاختيار أحداث بشرية قابلة للتدقيق.
10. الفريق يغطي أدوارًا ويحتاج قبول الأعضاء قبل اعتماده.

**القرار:** الحزمة الرابعة مكتملة تصميميًا لمتطلبات CLI وNEED وMAT. تبقى L وA معلقتين على بيانات فعلية، معايرة الأوزان والثقة والإنصاف، خدمات خادمية حية، واختبارات UAT والأداء.

## 25. الخطوة التالية
