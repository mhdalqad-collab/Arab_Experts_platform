# دليل Rollback وForward-Fix

## قبل النشر

- تثبيت Commit وصور الحاويات السابقة والجديدة بالـDigest.
- أخذ Backup والتحقق من SHA-256.
- تقدير مدة الترحيلات ونافذة التوقف.
- تحديد صاحب قرار التراجع وقناة الاتصال.
- عدم حذف أو استبدال بيانات قديمة ضمن ترحيل الإصدار.

## مؤشرات التراجع

- فشل Migration أو Ready Health Check.
- ارتفاع أخطاء 5xx أو فشل OIDC بصورة مستمرة.
- اختلاف بيانات أو فقد أثر تدقيقي.
- تجاوز SLO المتفق عليه دون استقرار سريع.

## مسار التطبيق

1. إيقاف توجيه الطلبات الجديدة عند الحاجة.
2. حفظ السجلات وCorrelation IDs والأدلة.
3. إعادة صورة التطبيق السابقة إذا كان المخطط متوافقًا.
4. استخدام Rollback SQL فقط بعد مراجعة DBA وتأكيد أثر البيانات.
5. إذا كان التراجع سيؤدي لفقد بيانات، يُفضّل Forward-Fix مع تعطيل الوظيفة المتأثرة.
6. تشغيل Smoke Tests والتحقق من البيانات بعد الإجراء.
7. توثيق القرار والمدة والأثر وفتح مراجعة ما بعد الحادث.

لا تُنفّذ استعادة Backup فوق قاعدة الإنتاج مباشرة. تُختبر الاستعادة أولًا في قاعدة منفصلة، ثم يتخذ فريق الإصدار وDBA القرار وفق حجم الضرر وRPO/RTO.
