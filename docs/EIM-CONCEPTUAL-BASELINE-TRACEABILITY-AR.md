# EIM-CB-002 — خط الأساس المفاهيمي ومصفوفة التتبع

**الحالة:** خط أساس مفاهيمي مجمد  
**الإصدار:** 2.0  
**تاريخ الاعتماد الفني:** 2026-07-30  
**النطاق:** مراجعة اتساق الحزم المفاهيمية، تثبيت ملكية الكيانات، توثيق القرارات، وإعلان بوابة الانتقال إلى النموذج المنطقي

## 1. النتيجة التنفيذية

اكتملت مراجعة أربع عشرة وثيقة مفاهيمية، منها قاموس المصطلحات وثلاث عشرة مواصفة مجال. تحتوي مواصفات المجالات على **456 قاعدة أعمال مرقمة**، إضافة إلى معايير القبول ودورات الحياة والكيانات المفاهيمية.

النتيجة:

- لا توجد فجوة مجال مفاهيمية حرجة تمنع الانتقال.
- لا توجد ازدواجية مقبولة لكيانات الحقيقة الأساسية.
- حسمت الحدود بين الهوية والعضوية والدور، وبين القدرة والخدمة والعرض، وبين الحاجة والطلب، وبين الدورة والطرح، وبين العقد والفاتورة، وبين التقييم والسمعة، وبين الملكية والترخيص.
- أصبحت القرارات المؤجلة محصورة في المعايرة والتوطين القانوني والتنفيذ المنطقي والتشغيلي.

> **اكتمال النموذج المفاهيمي لا يعني اكتمال البرمجيات؛ بل يعني أن ما يجب بناؤه، وحدوده، ومالكه، وقواعده، أصبح محددًا وقابلًا للتتبع.**

## 3. طبقات النموذج المتكامل

### 3.1 طبقة الهوية والأطراف

`Account → Party(Person|Organization) → Membership → ProfessionalRole/OrganizationRole`

- الحساب وسيلة دخول وليس الشخص.
- الطرف شخص أو منظمة وله هوية ثابتة.
- العضوية علاقة بين الطرف والشبكة.
- الدور المهني وصف نشاط، والدور الأمني تفويض صلاحيات.

### 3.2 طبقة الخبرة والمعنى

`Party → FingerprintPortfolio → ProfessionalFingerprint → Claim → Evidence → Verification → Confidence`

وترتبط جميعها بـ:

`ConceptScheme → Concept → SemanticMapping`

### 3.3 طبقة السوق والاحتياج

`Capability → ServiceDefinition → Offer`

مقابل:

`ClientNeed → NeedVersion → TaskFingerprint → ServiceRequest`

ثم:

`Eligibility → Candidate → MatchingRun → Recommendation → Shortlist → ClientDecision → Team`

### 3.4 طبقة التنفيذ

`ProviderResponse → ProposalVersion → Contract → Project → Baseline → Milestone/Deliverable → Acceptance → Closure`

### 3.5 طبقة المنتجات المعرفية

`LearningProduct/Course → ContentPackage → CourseOffering → Enrollment/Credential`

و:

`ResearchInitiative → ResearchProject → ResearchOutput/Publication → KnowledgeAsset`

### 3.6 طبقة المال والجودة والحقوق

`InvoiceEligibility → Invoice → Payment → Refund/Settlement`

`EligibleInteraction → Review → ReputationSnapshot`

`QualityPlan → Nonconformity → CorrectiveAction`

`Complaint → Investigation → Decision → Remedy/Appeal`

`IntellectualAsset → RightsBundle → License → Usage/Disclosure`

### 3.7 طبقة التحكم

`Policy → Control → AccessDecision → AuditEvent`

وتغطي الخصوصية والأمن والاحتفاظ والحوادث والتكاملات والقرارات الآلية.

## 5. ملكية الكيانات المتشابهة

### 5.1 Evidence وDocument

- `Evidence`: مطالبة وسياق ومصدر وملاءمة وحالة تحقق.
- `Document`: ملف أو بيانات وصفية يمكن أن تدعم دليلًا.
- يمكن للدليل امتلاك عدة مستندات، ويمكن لمستند واحد دعم أكثر من مطالبة وفق حقوقه.

### 5.2 ProfessionalFingerprint وTaskFingerprint

- البصمة المهنية تصف قدرة مثبتة لدى طرف ضمن سياق.
- بصمة المهمة تصف ما يحتاجه العميل.
- المطابقة تقارن نسختين ولا تدمجهما.

### 5.3 ServiceDefinition وOffer وProviderResponse وProposal

- الخدمة تعريف مستقر.
- العرض تجسيد تجاري قابل للبحث.
- الاستجابة جواب مقدم على طلب بعينه.
- المقترح وثيقة فنية وتجارية قابلة للتفاوض.

### 5.4 Course وContentPackage وCourseOffering

- الدورة هي المنتج التعلمي.
- الحقيبة هي المواد.
- الطرح هو التنفيذ.
- الحقوق يمكن أن تختلف بين الثلاثة.

### 5.5 Project وResearchProject

يشتركان في نمط الحوكمة العام، لكن مشروع البحث يضيف بروتوكولًا وأخلاقيات وبيانات ومخرجات علمية. يطبق في النموذج المنطقي نمط `Project` أساسي مع امتداد بحثي، لا نسخ كل حقول المشروع.

### 5.6 KnowledgeAsset وIntellectualAsset

- الأصل المعرفي ما يدار ويكتشف ويستخدم.
- الأصل الفكري هو موضوع الحقوق.
- قد يشيران إلى المورد نفسه بعلاقة، ولا يدمجان لأن دورة حياتهما مختلفة.

### 5.7 Review وQualityInspection وVerification

- التقييم رأي من طرف مؤهل.
- فحص الجودة اختبار مقابل معيار.
- التحقق يثبت ادعاء أو مصدرًا.
- لا يستبدل أحدها الآخر.

## 10. فحص التعارضات

| موضع التعارض المحتمل | الحسم |
|---|---|
| عقد المشروع مقابل العقد المالي | عقد واحد؛ المالية تستهلكه |
| مستند الدليل مقابل ملف التسليم | الملف مورد مشترك، والسياق علاقات منفصلة |
| مشروع عام مقابل مشروع بحث | أصل مشترك مع امتداد بحثي |
| تقييم الدورة والمدرب والمركز | موضوعات مستقلة |
| ملكية المعرفة مقابل إدارتها | IntellectualAsset للحقوق وKnowledgeAsset للإدارة |
| إخفاء المستخدم مقابل التزام العرض | السياسة القانونية/التعاقدية تقيد التفضيل |
| إغلاق الحساب مقابل الاحتفاظ | التعطيل لا يساوي المحو |
| قبول التسليم مقابل الفاتورة | القبول يولد أهلية فقط |
| سمعة مرتفعة مقابل أهلية ناقصة | لا تعوض الأهلية |
| موافقة المستخدم مقابل أساس المعالجة | الموافقة أساس محتمل وليست الافتراضي |

**نتيجة الفحص:** لا يوجد تعارض مفاهيمي مفتوح بدرجة حرجة.

## 12. قواعد التجميد والتغيير

من تاريخ هذا الخط الأساس:

- تعد وثائق المجال الأربع عشرة مرجعية.
- لا يغير اسم كيان أو حد مجال مباشرة داخل DDL أو الواجهة.
- أي تغيير مفاهيمي يبدأ بطلب تغيير `CCR`.
- يتضمن الطلب السبب والوثائق المتأثرة والكيانات والقواعد والواجهات والترحيل.
- يصنف التغيير: توضيح، متوافق، كاسر، أو قانوني عاجل.
- التغيير الكاسر ينشئ إصدار خط أساس جديدًا.
- التصحيح التحريري الذي لا يغير المعنى يوثق دون رفع الإصدار الرئيسي.

### دورة حياة طلب التغيير المفاهيمي

`مقترح → تحليل أثر → مراجعة ملاك المجالات → معتمد | مرفوض → مطبق → متحقق → مغلق`

## 13. بوابة الانتقال

يسمح بالانتقال إلى النموذج المنطقي لأن:

1. المجالات والحدود معرفة.
2. الكيانات المرجعية وملكيتها مثبتة.
3. دورات الحياة وقواعد الانتقال موجودة.
4. الأحداث العابرة للمجالات محددة.
5. الصلاحيات والخصوصية والحقوق مدمجة.
6. التعارضات المفاهيمية الحرجة مغلقة.
7. القرارات المؤجلة مصنفة ومملوكة.
8. يوجد اختبار آلي لوجود الحزم والقواعد والقرارات الأساسية.

## 14. معيار اكتمال المرحلة المفاهيمية

**الحكم:** مكتملة بنسبة **100% من حيث نطاق التصميم المفاهيمي المعتمد**، مع بقاء أعمال منطقية وتقنية وتشغيلية معلنة.

لا تعني النسبة أن كل شاشة وAPI وجدول أصبح منفذًا، وإنما أن المرحلة لم تعد تحتوي قرارًا بنيويًا مجهولًا يجب تخمينه أثناء البرمجة.

## 15. الخطوة التالية المعتمدة

1. اشتقاق النموذج المنطقي الموحد من سجل الكيانات المرجعية.
2. إنشاء قاموس بيانات مركزي واحد.
3. إعداد مصفوفة `Entity → Table → API → Screen → Permission → Test`.
4. مقارنة DDL الحالي بالخط الأساس وإصدار تقرير فرق.
5. إنشاء خطة ترحيل غير هدامة.
6. تحديث PostgreSQL DDL وOpenAPI والاختبارات على دفعات مجال.
