# EIM-MVP-001 — مصفوفة استكمال النموذج المفاهيمي وتغطية وظائف ومسارات MVP

**الإصدار:** V113 Working Baseline  
**مرجع الانطلاق:** EIM 6 Version 112 / Conceptual Baseline 2.0  
**الحالة:** قيد الإغلاق المرحلي  
**المبدأ:** لا تعديل على V112 المجمدة، ولا حذف أو دمج هادم لأي بيانات أو وظيفة سابقة.

## 1. قرار المرحلة

النموذج المفاهيمي الأساسي مكتمل ومعتمد بنسبة 100% من حيث المجالات والحدود والكيانات ودورات الحياة وقواعد الأعمال؛ إذ يغطي 14 وثيقة مفاهيمية و456 قاعدة أعمال. لذلك لا تهدف V113 إلى اختراع مجالات جديدة، بل إلى إثبات أن كل وظيفة ومسار MVP له:

`هدف ← ممثل/دور ← حالة استخدام ← كيان ← قاعدة أعمال ← صلاحية ← واجهة/API ← شاشة ← اختبار ← معيار قبول`

لا تعد الوظيفة مكتملة بمجرد وجود شاشة، ولا يعد الكيان مكتملًا بمجرد وجود جدول.

## 2. حالات التغطية المعتمدة

| الرمز | المعنى | شرط الاستخدام |
|---|---|---|
| C | مكتمل مفاهيميًا | المصطلح والحدود والكيانات والقواعد والحالات محسومة |
| D | ممثل في التصميم/النموذج التنفيذي | توجد شاشة أو API أو DDL أو اختبار مرجعي |
| L | يعمل بخدمة حية | يحفظ ويقرأ من مصدر حقيقة إنتاجي ويطبق الصلاحيات خادميًا |
| A | مقبول نهائيًا | اجتاز معايير القبول وUAT والأمن والأداء والتدقيق |

هدف هذه المرحلة هو **C + D لكل نطاق MVP**، ثم تحويل البنود المطلوبة للإطلاق إلى **L + A** في المرحلة التنفيذية. البيانات التجريبية و`localStorage` لا تحقق L.

## 4. مسارات MVP الملزمة

### J01 — الزائر: اكتشاف ومقارنة واتخاذ إجراء

`الرئيسية → البحث الموحد → تحديد نوع المورد → فلاتر مترابطة → نتائج جدولية → مقارنة → ملف عام → قائمة مختصرة أو تسجيل/دخول → طلب خدمة`

معيار القبول: لا يرى الزائر حقلًا غير مسموح، وتبقى أعمدة النتائج متطابقة، ويحفظ الاختيار بعد الدخول.

### J02 — مستخدم جديد: حساب وعضوية أولى

`الدخول والتسجيل → إنشاء حساب → تحقق → اختيار واحد أو أكثر من أنواع العضوية السبعة → دفع إن لزم → تعبئة بيانات العضوية المختارة → أدلة وخصوصية → مراجعة → إرسال → قرار`

معيار القبول: اختيار خبير يفتح بيانات الخبير، واختيار مركز يفتح بيانات المركز، ولا ينشأ Party مكرر.

### J03 — عضو: إضافة عضوية ثانية

`مركز الحساب → إضافة عضوية → اختيار النوع → تعبئة ملف جديد → إرسال → تبديل العضويات`

معيار القبول: يبقى الحساب والطرف موحدين، وتحفظ بيانات العضوية السابقة، وتطبق صلاحيات كل عضوية منفصلة.

### J04 — مهني: بناء ملف وبصمات موثقة

`هوية → مؤهلات → نبذة → تخصص 7×7×7 → خبرات/مشاريع/دورات → أدوار وخدمات → توفر وتسعير → أدلة متعددة → خصوصية كل حقل → نشر`

معيار القبول: يمكن إنشاء سجلات متعددة دون فقد السابق، والعودة تستعيد البيانات، وكل بصمة لها إصدار وسياق وأدلة ويقين.

### J05 — مركز تدريب: دورة وطرح ومدربون

`ملف المركز → التصنيف التدريبي → دورة/إصدار → مالك المحتوى وحقوقه → ربط مدربين أعضاء → إنشاء طرح → نمط/موعد/سعر/سعة → نشر`

معيار القبول: يسبق التصنيف إنشاء الدورة، ويكشف التشابه، ولا يخلط Course مع CourseOffering، ولا يقبل مدربًا غير مسجل إلا بحقل فارغ.

### J06 — عميل: تأسيس حساب مؤسسي وإدارة الفريق

`نوع العميل → الهوية القانونية → ممثل مخول → دعوات وأدوار → فروع/وحدات → وسائل اتصال وفوترة → فرص ومتابعات وSLA`

معيار القبول: لا يستطيع غير المخول إنشاء التزام، ولا يحذف آخر مالك، وتفصل بيانات المؤسسة عن المستخدم.

### J07 — عميل: بصمة احتياج وطلب خدمة

`اختيار نوع الاحتياج → الغرض والسياق → النطاق والمخرجات → معايير القبول → الميزانية والوقت → السرية والحقوق → أوزان المطابقة → تجميد النسخة → نشر/دعوة`

معيار القبول: تختلف بوابة الاكتمال حسب نوع الطلب، ولا تتغير النسخة المجمدة بصمت.

### J08 — مطابقة واختيار وتكوين فريق

`أهلية → حساب درجات موزونة → تفسير المطابقة والفجوات → بدائل متعددة → مقارنة → قائمة مختصرة → قرار العميل → دعوات الفريق → قبول الأدوار`

معيار القبول: الأهلية تسبق الترتيب، والعميل صاحب القرار، وكل تشغيل قابل لإعادة الإنتاج وفق إصدار المدخلات والأوزان.

### J09 — مقدم خدمة: استجابة ومقترح وعقد

`صندوق الطلبات → فحص الإفصاح → اهتمام/اعتذار → استجابة منظمة → مراجعة العميل → مقترح وإصدارات → تفاوض → قبول → توقيع مزدوج → عقد نافذ`

معيار القبول: لا يكشف الطلب بيانات محجوبة، ولا يعدل الإصدار المقبول، ولا ينفذ العقد قبل اكتمال التوقيعات.

### J10 — تنفيذ مشروع وتسليم وإغلاق

`عقد نافذ → مشروع → خط أساس → فريق → معالم → مخاطر/قضايا/قرارات → تسليم متعدد الملفات → استلام → قبول/رفض مسبب → فوترة → تغيير محكوم → إغلاق`

معيار القبول: الاستلام لا يساوي القبول، والتغيير لا يعدل الأصل، ولا يغلق المشروع مع التزامات مانعة.

### J11 — البحث عن دورة والتسجيل

`المجال التدريبي → التخصص → الدورة → جدول النتائج → مقارنة الطروحات → صفحة الدورة/المالك/المدرب → اختيار الطرح → تسجيل → فاتورة/دفع → تأكيد`

معيار القبول: نتيجة البحث صف واحد لكل طرح قابل للمقارنة، وتظهر اللغة والدولة والمدرب والمالك والتقييم والسعر.

### J12 — الاشتراك والدفع والاسترداد والتجديد

`خطة → فرد/مؤسسة → شهر/سنة → عدد العضويات/المقاعد → فاتورة → محاولة دفع → تسوية → تفعيل → تجديد أو إلغاء → استرداد كلي/جزئي`

معيار القبول: الحركات لا تحذف، وWebhook غير مكرر، والفاتورة والدفعة والاسترداد كيانات منفصلة.

### J13 — تقييم وسمعة وشكوى

`تفاعل مؤهل → تقييم متعدد المؤشرات → مراجعة نزاهة → نشر → لقطة سمعة → اعتراض/شكوى → تحقيق → قرار → علاج/استئناف`

معيار القبول: لا يوجد تقييم بلا تفاعل مؤهل، ولا تساوي الشكوى إدانة، وتظهر العينة ودرجة الثقة مع السمعة.

### J14 — بحث ونشر وفعالية ومعرفة

`مبادرة/مشروع بحث → أخلاقيات وحقوق → مخرج/منشور وإصدارات → مراجعة → نشر/تصحيح/سحب → أصل معرفي → فعالية/جلسة/مشاركة → استخدام وقياس أثر`

معيار القبول: يحفظ المصدر والإصدار والحقوق، ولا يتحول المنشور إلى دليل مهني تلقائيًا.

### J15 — الخصوصية والملف العام

`تفضيل على مستوى الحقل → أساس المعالجة → قرار وصول → إسقاط الملف العام → سحب موافقة/تغيير تفضيل → إعادة إسقاط → أثر تدقيق`

معيار القبول: يطبق القرار في الخادم والبحث والملف والملف المرفق، ولا تمحو الخصوصية التزام الاحتفاظ المشروع.

### J16 — إدارة المنصة والتدقيق

`قائمة عمل → تحقق صلاحية وفصل مهام → مطالبة مورد → قرار مسبب → إشعار → أثر تدقيق → مراقبة SLA → تصعيد/حادث → تصحيح ومراجعة`

معيار القبول: لا يعتمد المستخدم طلبه، ولا يعدل حدث التدقيق، وكل تجاوز استثنائي مؤقت ومسبب.

## 6. تعريف الاكتمال لكل وظيفة MVP

لا تغلق أي وظيفة إلا إذا تحققت الشروط العشرة:

1. مالك المجال والقرار معروفان.
2. المصطلحات والحدود لا تتعارض مع القاموس.
3. المدخلات والمخرجات والكيانات والإصدارات محددة.
4. دورة الحياة والانتقالات والفشل والإلغاء معرفة.
5. قواعد الأعمال والاستثناءات وعدم التكرار موثقة.
6. الصلاحيات والخصوصية والسرية والحقوق محددة.
7. الشاشة وAPI والجدول والحدث مرتبطة بمراجع واضحة.
8. الحالات الفارغة والخطأ والانتظار والتعارض مصممة.
9. اختبارات القبول الإيجابية والسلبية والأمنية موجودة.
10. لا تعتمد الوظيفة في التشغيل الحي على بيانات Demo أو حفظ محلي.

## 8. بوابة اعتماد MVP التصميمي

يعلن MVP مكتمل التصميم فقط عندما:

- تبلغ تغطية C وD نسبة 100% في المتطلبات الحرجة والعالية.
- لا توجد رحلة حرجة بلا حالة فشل أو رجوع أو حفظ مسودة.
- لا توجد شاشة يتيمة، أو API بلا مالك، أو جدول بلا كيان مفاهيمي، أو قاعدة بلا اختبار.
- تنجح مصفوفة الصلاحيات والخصوصية في السيناريوهات السلبية.
- تتطابق أسماء الكيانات في القاموس والنموذج المنطقي وDDL وAPI والشاشات.
- يصدر سجل فجوات منفصل لما يحتاج خدمة حية، دون خلطه باكتمال التصميم.

## 9. الخطوة التنفيذية التالية

إنشاء **سجل متطلبات MVP المرقم ومصفوفة التتبع التفصيلية** للحزمة الأولى. يبدأ بالوظائف الحرجة: الحساب والطرف والعضوية، الملف المهني والخصوصية، البحث، احتياج العميل، المطابقة، الدورة والطرح، ثم دورة الخدمة والعقد والمشروع والمال.
