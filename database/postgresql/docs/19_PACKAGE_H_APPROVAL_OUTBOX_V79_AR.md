# الحزمة H — استئناف الموافقة وتسليم Outbox — V79

## النتيجة

تكمل هذه الحزمة المسار غير المتزامن لأوامر قضايا الخدمة دون تغيير وضع سير
العمل الحالي `MONITOR_ONLY`. وهي لا تربط العرض التجريبي D1 مباشرة بقاعدة
PostgreSQL؛ بل تثبت واجهة التنفيذ الإنتاجية التي تستدعيها طبقة API عند توفير
اتصال PostgreSQL في بيئة التشغيل.

## 1. اكتمال الموافقات

الدالة:

`governance.decide_service_case_transition_approval(...)`

- تقبل القرار من حساب نشط فقط.
- تستخرج هوية الطرف والدور من IAM/RBAC ولا تثق بدور يرسله العميل.
- تقصر الاعتماد على `PLATFORM_OPERATOR` أو `PLATFORM_ADMIN`.
- تطبق فصل المهام بواسطة القاعدة القائمة التي تمنع مقدم الطلب من اعتماد طلبه.
- تشترط سببًا للرفض أو الإعادة.
- تحسب النصاب وتحدث حالة طلب الموافقة.
- تستدعي الاستئناف آليًا بعد اكتمال النصاب.

الدالة:

`delivery.resume_approved_service_case_transition(...)`

- تقفل طلب الموافقة ومحاولة الانتقال وقضية الخدمة.
- تمنع التنفيذ إن تغيرت مرحلة القضية أثناء انتظار الموافقة.
- تجعل إعادة الاستدعاء آمنة ولا تكرر الانتقال.
- تسجل حدث المرحلة وتحدث إيصال الأمر.
- تكتب حدث Outbox في المعاملة نفسها.

## 2. تسليم Outbox

الجدول `integration.outbox_dispatch_leases` يحتفظ بكل محاولة حجز ولا يحذف
سجلًا سابقًا.

الدالة `integration.claim_outbox_events(...)`:

- تستخدم `FOR UPDATE SKIP LOCKED` لتشغيل عدة عمال بأمان.
- تحدد حجم الدفعة ومدة الحجز.
- تحرر الحجوزات المنتهية تلقائيًا.

الدالة `integration.complete_outbox_dispatch(...)`:

- تؤكد النشر بصورة idempotent.
- تزيد عداد المحاولات مرة واحدة للحجز الفعال.
- تطبق تأخيرًا أسيًا محدودًا.
- تحول الحدث إلى `DEAD_LETTER` بعد الحد الأقصى.

## 3. عقد طبقة API

عند ربط التطبيق الإنتاجي بـPostgreSQL:

1. `POST /api/v1/service-cases/{id}/commands` يستدعي
   `delivery.execute_service_case_command`.
2. `POST /api/v1/workflow-approvals/{id}/decisions` يستدعي
   `governance.decide_service_case_transition_approval`.
3. عامل داخلي يستدعي `integration.claim_outbox_events` ثم ينشر الحدث، وبعدها
   يستدعي `integration.complete_outbox_dispatch`.
4. ترسل طبقة API معرف حساب المستخدم فقط؛ استخراج الطرف والدور يبقى داخل
   قاعدة البيانات.
5. يجب تمرير `Idempotency-Key` و`expectedRowVersion` في أمر الانتقال.

## 4. حالات القبول الحرجة

- عاملان متزامنان لا يحصلان على الحدث نفسه بحجز فعال.
- إعادة إكمال الحجز لا تزيد عدد المحاولات مرتين.
- فشل النشر يعيد الجدولة ولا يفقد الحدث.
- الوصول للحد الأقصى ينتج `DEAD_LETTER` قابلًا للتدقيق.
- الموافقة الذاتية مرفوضة.
- الاعتماد دون دور مخول مرفوض.
- تغير مرحلة القضية أثناء الانتظار يمنع استئناف انتقال قديم.
- إعادة استدعاء الاستئناف بعد التنفيذ تعيد نتيجة آمنة ولا تكرر الحدث.

## 5. التفعيل

لا تغيّر هذه الحزمة سير العمل إلى `ENFORCING`. الانتقال إلى المنع الفعلي قرار
تشغيلي لاحق، بعد تشغيل اختبارات PostgreSQL التكاملية ومراجعة تقارير وضع
المراقبة واعتماد نسخة سير عمل جديدة.
