# الحزمة G — مشغل أوامر قضية الخدمة

## 1. الهدف

تنفذ الحزمة G دالة PostgreSQL واحدة تمثل البوابة المعتمدة مستقبلًا لتغيير
مرحلة قضية الخدمة:

`delivery.execute_service_case_command(...)`

تنفذ الدالة التحقق والتسجيل والانتقال وإنتاج الحدث داخل معاملة واحدة. ويبقى
إصدار سير العمل الحالي في وضع `MONITOR_ONLY`، لذلك لا تبدأ الحزمة المنع
الإلزامي.

## 2. ضمانات المشغل

### 2.1 الهوية الموثوقة

تستقبل الدالة معرّف حساب المستخدم، ثم تستخرج الشخص المرتبط به من
`iam.user_accounts`. لا تستقبل اسم الدور من الواجهة ولا تثق به.

يشترط:

- وجود الحساب.
- أن تكون حالة الحساب `ACTIVE`.
- وجود تكليف دور نشط وغير منتهي.
- أن يكون الدور ضمن الأدوار المسموحة للانتقال.

### 2.2 منع التكرار

كل أمر يحمل مفتاح `idempotency_key`. عند تكرار الطلب:

- إذا كانت البصمة مطابقة، تعاد النتيجة المحفوظة.
- إذا استُخدم المفتاح لطلب مختلف، يرفض الطلب.
- لا ينشأ انتقال أو حدث ثانٍ.

تشمل بصمة الطلب القضية والأمر والمرحلة المطلوبة ونسخة الصف والسبب والتحقق
الإضافي وحمولة الطلب.

### 2.3 القفل المتفائل

يقفل المشغل صف قضية الخدمة أثناء التنفيذ، ويقارن `expected_row_version`
بالنسخة الحالية. عند الاختلاف يعيد `ROW_VERSION_CONFLICT` ولا ينفذ
الانتقال، مما يمنع ضياع تحديث متزامن.

### 2.4 تقييم الانتقال

يفحص المشغل:

1. وجود قاعدة انتقال مطابقة.
2. صلاحية الدور الفعلية.
3. اكتمال البوابات المانعة.
4. وجود السبب عند اشتراطه.
5. تحقق الهوية الإضافي عند اشتراطه.
6. الحاجة إلى اعتماد منفصل.

وتحفظ النتيجة في `service_case_transition_attempts`.

### 2.5 وضع المراقبة

في `MONITOR_ONLY`:

- ينفذ الانتقال حتى لا تتعطل العمليات القائمة.
- يحول المخالفة المحتملة إلى `ALLOW_WITH_WARNING`.
- ينشئ استثناء مراقبة قابلًا للمراجعة.
- لا يخفي سبب التحذير.

لا يسمح قيد قاعدة البيانات بتسجيل قرار `BLOCK` في وضع المراقبة.

### 2.6 الاعتماد وفصل الواجبات

عند الوضع الإلزامي، إذا كان الانتقال صالحًا لكنه يحتاج اعتمادًا:

- لا ينفذ الانتقال.
- ينشأ `governance.approval_request`.
- ترتبط محاولة الانتقال بطلب الاعتماد.
- لا يستطيع مقدم الطلب اعتماد طلبه بسبب ضابط فصل الواجبات القائم.

تكون نتيجة فحص فصل الواجبات غير محسومة حتى يصدر قرار المعتمد.

### 2.7 المعاملة وOutbox

عند تنفيذ الانتقال تحفظ العناصر التالية في المعاملة نفسها:

- تحديث مرحلة قضية الخدمة.
- حدث المرحلة في السجل الزمني.
- نتيجة محاولة الانتقال.
- إيصال الأمر.
- حدث `integration.outbox_events`.
- رابط الحدث بمحاولة الانتقال.

إذا فشل أي جزء تفشل المعاملة كلها، فلا توجد حالة ناجحة بلا حدث أو حدث بلا
انتقال.

## 3. النتائج الممكنة

- `SUCCEEDED`: نُفذ الانتقال.
- `PENDING_APPROVAL`: لم ينفذ وينتظر الاعتماد.
- `REJECTED`: لم ينفذ بسبب قاعدة مانعة أو تعارض نسخة.
- `replayed=true`: أعيدت نتيجة أمر سابق مطابق.

## 4. الرؤية التشغيلية

يعرض `delivery.v_service_case_command_operations`:

- القضية والأمر.
- الفاعل.
- حالة التنفيذ.
- قرار تقييم القاعدة.
- وضع التطبيق.
- وقت الاستلام والإكمال والتنفيذ.
- معرّف الارتباط للتتبع بين الخدمات.

## 5. ضوابط الاستخدام

1. لا تمنح الواجهة صلاحية تحديث `service_cases` مباشرة.
2. لا يولد مفتاح التكرار داخل الدالة؛ يولده العميل مرة واحدة لكل نية عمل.
3. لا يعاد استخدام المفتاح لأمر مختلف.
4. لا يعتمد التطبيق على رسالة الخطأ فقط؛ يقرأ رمز النتيجة.
5. لا تعدل نتيجة الأمر بعد اكتماله.
6. لا ينشر عامل Outbox الحدث مرتين.
7. لا يحول سير العمل إلى الإلزام قبل اختبارات التزامن والتكامل.

## 6. التراجع

يرفض ملف التراجع إزالة المشغل إذا كان قد عالج أمرًا مكتملًا أو نفذ انتقالًا.
هذا يمنع إزالة الدالة مع بقاء سجلات تشغيلية تعتمد عليها.

## 7. ما لم تنفذه الحزمة

- لم تربط واجهة API بالمشغل.
- لم تفعل وضع `ENFORCING`.
- لم تنفذ معالج استكمال الانتقال بعد الاعتماد.
- لم تضف عامل نشر Outbox.
- لم تمنع الكتابة المباشرة عبر صلاحيات قاعدة البيانات بعد.

## 8. الخطوة التالية

الحزمة H المقترحة: واجهة API لمشغل الأوامر ومعالج استكمال الاعتماد وعامل
Outbox، مع اختبارات PostgreSQL حقيقية للتزامن والتكرار والانقطاع، ثم تقارير
مراقبة تحدد جاهزية الانتقال من المراقبة إلى الإلزام.
